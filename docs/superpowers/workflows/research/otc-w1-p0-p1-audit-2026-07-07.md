### 2.1 Q-F1（P0 Major）：Exemption 编号格式与 lessonDistiller 写盘格式不一致

**本仓库修复内容**：
lottery-notification 将 specReview/qualityReviewer Exemption 的编号格式从 `L-YYYYMMDD-NN` 改为 `L-<timestamp>`（如 `L-20260701T103320Z`），并显式注明"与 lessons.md 中 `## L-<ts>` 条目格式一致"，确保 reviewer 查找的编号格式与 lessonDistiller 写入的格式完全匹配。

**OTC 仓库实际状态**：

- **OTC lessonDistiller 写盘格式**（run-plans.js L1072, lib.js L1157）：
  ```
  ## L-<ts>
  ```
  lessonDistiller prompt 明确指示 append 时用 `## L-<ts>` 格式（时间戳，如 `L-20260701T103320Z`）。

- **OTC specReview Exemption 格式**（run-plans.js L862）：
  ```
  1. 查 commit message / 代码注释是否有 L-YYYYMMDD-NN 编号（如 L-2026-07-07-002）。
  ```

- **OTC qualityReviewer Exemption 格式**（run-plans.js L892）：
  ```
  W1-5e (2026-07-07): implementor 按 {{lessonsPath}} 中记录的 lesson 加固代码时（commit message / 代码注释含 L-YYYYMMDD-NN 编号），以下维度**不报 finding**：
  ```

**判定**: ❌

**判定理由**：
OTC 的 lessonDistiller 写入 `## L-<ts>`（时间戳格式，如 `L-20260701T103320Z`），但 specReview 和 qualityReviewer 的 Exemption 段落却指示 reviewer 查找 `L-YYYYMMDD-NN` 格式（如 `L-2026-07-07-002`）。两者格式不一致——reviewer 按 `L-YYYYMMDD-NN` 找不到 lessonDistiller 实际写入的 `L-<ts>` 编号，Exemption 闭环失效，implementor 加固的代码仍会被报为 EXTRA，导致 reviewer ↔ implementor 振荡。本仓库修复的关键是"格式一致"，OTC 两处格式不一致即构成同样的 P0 问题。

**证据**：
- OTC run-plans.js L862: `L-YYYYMMDD-NN 编号（如 L-2026-07-07-002）`
- OTC run-plans.js L892: `L-YYYYMMDD-NN 编号`
- OTC run-plans.js L1072: `## L-<ts>`（lessonDistiller 写盘格式）
- OTC lib.js L1157: `## L-<ts>`（同步副本）
- 对比 lottery-notification run-plans.js L871: `L-<timestamp> 编号（如 L-20260701T103320Z，与 lessons.md 中 ## L-<ts> 条目格式一致）`

### 2.4 H-F2（P0 Major）：bootstrap step 5a 用 git add && git commit 两步 + 硬编码路径

**本仓库修复内容**：
lottery-notification 将 bootstrap step 5a 的 lessons.md 提交从两步 `git add <path> && git commit -m "..."` 改为一步 `git commit -m "..." <lessonsPath>`，防止 add 成功但 commit 失败后 step 5b 的 `git reset --hard HEAD` 清除 staging 区域的 lessons.md 改动导致数据丢失；同时将硬编码路径 `docs/superpowers/lessons.md` 改为动态 `lessonsPath` 变量。

OTC bootstrap step 5a（run-plans.js L787）：
```

```

两步操作 + 硬编码路径 `docs/superpowers/lessons.md`。

**判定**: ❌

**判定理由**：

**证据**：
- OTC run-plans.js L787: `git add docs/superpowers/lessons.md && git commit -m "..."` — 两步 + 硬编码
- OTC run-plans.js L789: `git reset --hard HEAD to clean` — step 5b 会清除 staging
- 对比 lottery-notification run-plans.js L793: `git commit -m "chore(workflow): auto-commit lessons.md from interrupted run" <lessonsPath> (preserve knowledge base, best-effort; H-F2 2026-07-07: 用 git commit <path> 一步到位不预 staged, 防 add 成功 commit 失败后 5b reset --hard 清除 staging)`

### 2.8 H-F6（P1 Minor）：normalizeFilePath 未用 typeof 严格检查

**本仓库修复内容**：
lottery-notification 将 normalizeFilePath 的入参检查从 `if (!p) return p` + `String(p)` 改为 `if (typeof p !== 'string' || !p) return p`，非字符串原样返回不强制 String 化，避免 `0` → `'0'` / `{file:'a.py'}` → `'[object Object]'` 污染 groupFindingsByFile 的分组键。

**OTC 仓库实际状态**：

OTC normalizeFilePath（run-plans.js L174-176）：
```javascript
function normalizeFilePath(p) {
  if (!p) return p
  return String(p).replace(/\\/g, '/').replace(/^.*?\/(src|tests|docs|data|logs)\//i, '$1/')
}
```

`if (!p) return p` + `String(p).replace(...)`。

**判定**: ❌

**判定理由**：
`if (!p)` 仅拦截 falsy 值（0 / '' / null / undefined / false），但 `0` 是 falsy → 返回 0（number），下游 Set.add(0) 不会报错但污染分组键。更严重的是非 falsy 的非字符串：`String({file:'a.py'})` → `'[object Object]'` → 归一化后仍为 `'[object Object]'` → groupFindingsByFile 把所有对象类 file 合并到同一分组 → cross-reviewer 重叠检测误报。`typeof p !== 'string'` 严格检查可拦截所有非字符串输入，原样返回不污染。

**证据**：
- OTC run-plans.js L175: `if (!p) return p` — 仅 falsy 检查
- OTC run-plans.js L176: `String(p).replace(...)` — 强制 String 化
- OTC lib.js L107-108: 同步副本，同样问题
- 对比 lottery-notification lib.js L113: `if (typeof p !== 'string' || !p) return p` — typeof 严格检查
